# 大脑在哪儿：算力板和软件分层

你推一下手柄的摇杆，机器狗往前迈了一步。

这一步大约用时零点三到零点五秒。在这段时间里，机器狗身上的控制程序已经运行了上百次，每一次都要读一遍所有关节和 IMU 的数据，算出 12 个关节下一刻该去哪，再把指令发下去；每个关节里的驱动芯片又在每秒上万次地调整电流。

这一章拆的是这些计算发生在哪里，以及一套机器人软件长什么样。对想转行做机器人软件的人，这是全书最该细读的一章。

## 两台电脑

打开机器人的身体，管计算的往往不止一块板子。

宇树的产品基本是“两台电脑”的结构：

- **主控**：负责站稳、走路、跑跳这些运动控制，跑的是厂商自己写的程序。G1、Go2 官网写的是“8 核高性能 CPU”。所有版本都有。
- **开发算力**：留给用户跑自己的程序，比如视觉识别、导航、大模型。Go2 EDU、G1 EDU 可以选装高算力模组，官网举的例子是英伟达 Orin（40–100 TOPS）。

H1 写得最清楚：标配一颗 Intel Core i5 负责“平台功能”，一颗 Core i7 留给“用户开发”，还可以再加 Orin NX。

为什么要分开？因为**站稳是头等大事**。用户写的程序可能有 bug，可能卡死，可能把内存吃光。如果它和运动控制挤在同一台电脑上，用户程序一出事，机器人就可能当场摔倒。分开以后，开发板怎么折腾都影响不到主控，主控只听开发板发来的“指令”，而且可以拒绝不安全的指令。

这种“安全的归安全、开放的归开放”的设计，在汽车、飞机上也很常见。

## 软件像一栋楼

一台腿足机器人的软件，可以想象成一栋五层楼，越往下越快、越要可靠：

![图 9-1　腿足机器人的软件分层（频率为典型量级）](图/f09-软件分层.pdf)

| 楼层 | 在干什么 | 典型频率 | 跑在哪 |
|------|------------------|---------|---------|
| 5 应用 | 导航、对话、任务规划、手机 App | 每秒几次 | 开发板 / 云端 |
| 4 运动服务 | 接收“往前走 0.5 m/s”，生成步态、保持平衡 | 每秒几十到几百次 | 主控 |
| 3 低层控制 | 给每个关节发“目标角度、刚度、阻尼” | 每秒 500–1000 次 | 主控 |
| 2 关节控制 | 让关节跟上目标，算出要多大电流 | 每秒数千次 | 关节里的驱动芯片 |
| 1 电流控制 | FOC，控制线圈电流 | 每秒上万次 | 关节里的驱动芯片 |

: 表 9-1　机器人软件的五层

普通用户只碰得到第 5 层：用 App 或手柄告诉它“走”“坐下”“跳个舞”。EDU 版用户可以下到第 4 层和第 3 层：给运动服务发速度指令，或者干脆关掉运动服务，自己直接控制每个关节。

第 1、2 层烧在关节的芯片里，一般不开放。

## 第 3 层：五个数控制一个关节

第 3 层是整个腿足机器人领域最重要的接口，值得细看。

宇树的低层指令叫 `lowcmd`。对每一个关节，它只发五个数：

- `q`：目标角度
- `dq`：目标角速度
- `kp`：刚度
- `kd`：阻尼
- `tau`：前馈扭矩

关节里的驱动芯片收到这五个数，每一次都按下面这个公式算出要输出的扭矩：

$$\tau_{\text{输出}} = \tau_{\text{前馈}} + k_p\,(q_{\text{目标}} - q) + k_d\,(\dot q_{\text{目标}} - \dot q)$$

看着复杂，其实就是给关节装了一根**虚拟的弹簧**和一个**虚拟的减震器**：

- 关节偏离目标角度越多，“弹簧”往回拉得越用力，`kp` 就是弹簧有多硬。
- 关节动得越快，“减震器”越往回拽，`kd` 就是减震器有多黏。
- `tau` 是额外加的一把力，比如事先知道要撑住多少重量，就直接加上。

GO-M8010-6 官网写的控制指令正好是这五样：扭矩、角度、角速度、刚度、阻尼。

这五个数的组合，能让一个关节变成完全不同的东西：

- `kp`、`kd` 设成 0，只给 `tau`：纯扭矩控制，关节完全“软”，想要多大力就给多大力。
- `kp` 很大：关节像一根硬棍子，死死守住目标角度。
- `kp` 适中：关节像一根弹簧，被推会让，松手会回。

第 11 章会讲到，这种“可调硬度的弹簧腿”正是腿足机器人走得稳的秘诀之一；第 12 章会讲到，强化学习训练出来的策略，输出的往往就是这里的 `q`，`kp` 和 `kd` 则提前设好。

::: engineer
**一段让机器狗站起来的伪代码**

下面是示意性的伪代码，不是宇树 SDK 的真实接口，变量名和数值都是为了讲清楚思路。真实代码请看官方的 unitree_sdk2 和 unitree_mujoco 示例。

```python
# 伪代码：用 2 秒把 12 个关节从趴下的姿势平滑地挪到站立姿势
stand = [0.0, 0.67, -1.30] * 4   # 每条腿：髋侧摆、髋前摆、膝（单位：弧度，示意值）
start = read_lowstate().q        # 记下当前 12 个关节的角度
for step in range(1000):         # 每 2 毫秒一次，共 2 秒
    a = (step + 1) / 1000        # 插值系数：0 → 1
    for j in range(12):
        cmd[j].q   = (1 - a) * start[j] + a * stand[j]
        cmd[j].dq  = 0.0
        cmd[j].kp  = 60.0        # 刚度（示意值）
        cmd[j].kd  = 5.0         # 阻尼（示意值）
        cmd[j].tau = 0.0
    publish_lowcmd(cmd)
    wait_until_next_tick(0.002)
```

几个要点：

- 目标角度要**慢慢插值**过去，不能一下子跳到站立姿势，否则关节会以最大扭矩猛甩，非常危险。
- `kp` 太小站不起来，太大会抖；`kd` 太小会晃，太大会“发黏”迟钝。
- 在真机上做低层控制，必须先把机载的运动服务关掉（官方文档里叫切换模式、进入调试模式），否则两套程序会抢着控制同一组关节。
- 真机第一次跑，一定先吊起来、把增益调小、手边有急停。
:::

## 第 4 层：运动服务

大多数时候，开发者不需要自己管 12 个关节。宇树的主控里跑着一套运动服务（官方叫“运动模式”），对外提供更高层的接口：设定前进、横移、转向的速度，站起、趴下，切换步态，做几个预设动作。

宇树 ROS 2 仓库的说明里，这类高层指令通过 `/api/sport/request` 发出，运动状态通过 `sportmodestate` 读回。你告诉它“以 0.5 m/s 往前走”，至于每条腿怎么迈、怎么保持平衡，它自己负责。

做导航、做应用的开发者，基本只用这一层；做运动控制研究的，才需要下到第 3 层。

## DDS：机器人内部的广播电台

楼层之间、程序之间怎么传消息？宇树的第二代软件开发包 unitree_sdk2，底层用的是一种叫 **DDS**（数据分发服务）的通信中间件，具体实现是开源的 CycloneDDS。

DDS 的工作方式像广播电台：

- 发消息的程序是“电台”，在某个“频道”（DDS 里叫**话题**）上广播，比如 `lowstate` 频道不停地播所有关节和 IMU 的最新状态。
- 想听的程序是“收音机”，调到这个频道就能收到，不需要知道电台在哪台电脑上。
- 一个频道可以有很多收音机，一台收音机也可以同时听很多频道。

这种“发布—订阅”的方式好处很多：程序之间互不依赖，加一个新功能只要多订阅几个话题；在同一个局域网里，电脑和机器人之间的通信也是同一套。

最关键的一点：**机器人操作系统 ROS 2 的底层用的也是 DDS。** 宇树的 ROS 2 仓库说明里写得很明白：既然底层都是 DDS，ROS 2 的消息可以直接和机器人通信，不需要再包一层 SDK。这意味着全世界 ROS 2 生态里现成的工具——可视化、建图、导航、录数据——拿过来就能和宇树的机器人对接。宇树推荐的环境是 Ubuntu 22.04 加 ROS 2 Humble。

对开发者来说，这是宇树机器人在研究圈流行的一个重要原因：**接口是标准的。**

**几个常用话题**

据宇树 ROS 2 仓库的说明（以 Go2、B2 为例）：

| 话题 | 方向 | 内容 |
|------------|---------|---------------|
| `lowstate` | 机器人 → 你 | 电机状态、IMU、电源 |
| `lowcmd` | 你 → 机器人 | 每个电机的扭矩、角度、速度指令 |
| `sportmodestate` | 机器人 → 你 | 机身位置、速度、足端等运动状态 |
| `/api/sport/request` | 你 → 机器人 | 高层运动指令 |
| `/wirelesscontroller` | 机器人 → 你 | 遥控器摇杆和按键 |

有的话题带 `lf/` 前缀，表示低频版本。在 DDS 层面，ROS 2 的话题名前面会自动加上 `rt/`，所以你在 SDK 的示例里看到的是 `rt/lowcmd` 这样的名字——宇树的话题命名是按 ROS 2 的规矩来的，两边才能直接互通。

## 基础款和 EDU：同一块主控，不同的门

讲到这里，第 2 章那个“二次开发”的问题就彻底清楚了。

基础款和 EDU 版的主控、运动服务基本是同一套。区别在于“门开了几扇”：基础款只开了第 5 层的门，你只能用 App 和手柄调用预设功能；EDU 版把第 4 层、第 3 层的门也打开了，再加上开发算力和更多接口。招股书的说法是，EDU 款“支持用户加装模型算法、软件程序及硬件配置等，实现自定义运动、模型开发测试、自主导航、场景交互等功能”。

对研究者和转行者来说，买机器人买的其实是这几扇门。

## 机器人上的大模型跑在哪

最后说一下大家关心的“机器人接上大模型”。

语音对话、看图回答这类功能，计算量大，常见的做法是机器人把声音和图像传到云端，由云端的大模型处理，再把回答和指令传回来。这样机器人本身不用背着大显卡，但离不开网络，也带来隐私的问题（第 17 章细说）。

想离线运行，就得靠开发板上的算力。几十 TOPS 的 Orin 能跑中小规模的视觉模型和语言模型，跑不动最大的那些。第 15 章会讲到，具身大模型也在往“快慢两层”拆：慢的大模型在大算力上想“做什么”，快的小策略在机器人身上管“怎么做”。

::: takeaway
机器人的软件像一栋楼：越往下越快、越要可靠；EDU 版的价值，是给你一把能进底层的钥匙，而 DDS 让这把钥匙和整个 ROS 2 世界通用。
:::
